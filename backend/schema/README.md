# База данных Tipro

База — PostgreSQL 18. На настроенном компьютере её рабочие файлы находятся в `backend/.runtime/pgdata`. Этот каталог исключён из Git: после клонирования приложение создаёт новую пустую БД, а не копию данных автора. Подготовка окружения и локальной базы описана в [основном README](../../README.md).

В репозитории находятся:

- **`tipro.sql`** — актуальная полная структура: рестораны, сотрудники, платежи, QR, цели, сессии, события webhook, аудит, служебные таблицы, индексы и ограничения. Включает поля одобрения ресторана, `used_at`, привязку v3-QR к сотруднику и чеку на 24 часа, CREATED в статусах платежа, маски реквизитов, audit_events и служебную версию Alembic `0008_receipt_payments`.
- `legacy.sql` — исходная структура Users.sql до изменений приложения.
- `../alembic/versions/` — история миграций.
- `../app/seed.py` — отдельное идемпотентное заполнение демонстрационными данными.

SQL-структура не содержит аккаунтов, паролей, QR-токенов и истории платежей. Единственная служебная запись — версия Alembic, чтобы последующий `upgrade head` не создавал таблицы повторно.

## Создать новую базу

На macOS или Windows запустите из корня:

```sh
npm start
```

При первом запуске создаются `.venv`, зависимости и `.env`, затем отдельная пустая PostgreSQL и все таблицы через миграции. Нужны установленные Node.js, Python 3.12+ и PostgreSQL 18. Seed автоматически не выполняется.

В новой базе нет администратора. После запуска приложения из второго терминала:

```sh
npm run create:admin -- --email admin@example.com --name "Администратор платформы"
```

Пароль задаётся в терминале. Новые рестораны регистрируются со статусом PENDING; администратор подтверждает их в своём кабинете.

## Альтернатива: импортировать готовую SQL-структуру

Этот способ нужен, если вы хотите создать таблицы через SQL-снимок вместо первоначальных миграций. Импортируйте файл только в **новую пустую** базу. На уже работающем сервере, из корня проекта:

```sh
createdb -h 127.0.0.1 -p 55432 -U tipro tipro_schema
psql -h 127.0.0.1 -p 55432 -U tipro -d tipro_schema -v ON_ERROR_STOP=1 --single-transaction -f backend/schema/tipro.sql
```

Подставьте свои адрес, порт и пользователя; пароль вводится средствами PostgreSQL. Укажите `tipro_schema` в DATABASE_URL файла `backend/.env`, затем выполните `npm start`. Лаунчер применит только ещё не выполненные миграции. Не импортируйте `legacy.sql` поверх `tipro.sql` и не выполняйте импорт поверх рабочей базы с данными.

## Данные из исходного Users.sql

Users.sql — бинарный custom dump PostgreSQL, он восстанавливается через `pg_restore`, а не `psql -f`. Исходный файл не включён в Git. Восстановление в отдельную пустую базу и последующие миграции описаны в [инструкции бэкенда](../README.md#дамп-и-существующая-схема).

На компьютере автора 4 ноября 2026 года были восстановлены исходные 20 ресторанов, 60 сотрудников, 100 платежей и 100 QR. Резервная копия прежнего состояния сохранена локально в `.runtime/backups`. Новые миграции сохраняют историю; прежние QR без привязки к чеку отключены, новые требуют сотрудника, сумму и уникальный идентификатор чека и действуют 24 часа. Миграция 0008 также преобразует прежние реквизиты сотрудников в маски: полные значения не сохраняются. История платежей остаётся на месте.

## Необязательные демоданные

После подготовки базы seed можно запустить отдельно. macOS, из корня:

```sh
cd backend
.venv/bin/python -m app.seed
```

Windows PowerShell, из корня:

```powershell
Set-Location backend
.\.venv\Scripts\python.exe -m app.seed
```

Seed не восстанавливает реальные аккаунты или платежи. Создаваемые им демоаккаунты используют DEMO_PASSWORD из `.env`. Повторный запуск не перезаписывает существующие пароли и не продлевает срок QR.

## Обновить SQL-снимок

После применения новых миграций из корня:

```sh
npm run db:schema
```

Скрипт экспортирует только структуру и служебную версию миграций. Если pg_dump находится в другой папке, задайте TIPRO_PG_BIN. PowerShell:

```powershell
$env:TIPRO_PG_BIN = 'C:\Program Files\PostgreSQL\18\bin'
npm run db:schema
```

macOS:

```sh
TIPRO_PG_BIN=/путь/к/postgresql/bin npm run db:schema
```

## Что переносить и хранить локально

Код, зависимости, миграции и SQL-структура находятся в Git. `.env`, `.venv`, `backend/.runtime/pgdata`, исходный Users.sql и приватные резервные копии остаются локальными. Для переноса реальных записей нужна отдельная приватная резервная копия: каталог работающей PostgreSQL не является переносимым SQL-дампом. Время платежей хранится в UTC; часовой пояс браузера используется при построении графиков и отборе по календарным дням, без изменения записей.
