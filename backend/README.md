# Tipro backend

FastAPI + PostgreSQL 18 + SQLAlchemy 2 asyncpg. Существующий Vue-фронтенд использует `/api`; Swagger: http://127.0.0.1:8000/docs. Настоящих списаний нет.

## Быстрый запуск

Из корня на macOS или Windows:

```sh
npm start
```

Или откройте `Запустить Tipro.command` на macOS / `Запустить Tipro.bat` на Windows. Нужны установленные Node.js с npm, Python 3.12+ и PostgreSQL 18. Первое выполнение создаёт локальную `.venv`, устанавливает зависимости, генерирует `.env` при его отсутствии и запускает базу, миграции, API и Vue. Рабочие файлы и секреты существующего проекта не перезаписываются. Seed автоматически не выполняется.

На новом компьютере создаётся пустая локальная БД в `backend/.runtime/pgdata`, порт 55432. На компьютере автора в этот каталог 4 ноября 2026 года восстановлены исходные данные Users.sql: 20 ресторанов, 60 сотрудников, 100 платежей и 100 исторических QR; прежнее состояние сохранено в `.runtime/backups`. Эти локальные записи не входят в GitHub и не появляются при клонировании.

Дождитесь «Tipro готов», оставьте терминал открытым. Ctrl+C завершает только серверы этого лаунчера; PostgreSQL и ранее работавшие серверы продолжают работу. Для запуска без браузера используйте `npm start -- --no-open`. Раздельные команды — `npm run dev:api` и `npm run dev`.

Лаунчер определяет IPv4 компьютера, передаёт его в FRONTEND_URL и CORS на время запуска. Для выбора адреса используйте TIPRO_LAN_HOST. Телефон и компьютер должны находиться в одной Wi-Fi сети; запросы к /api проходят через Vue, API и PostgreSQL слушают loopback. При изменении IP перевыпустите PNG с актуальным URL. Если уже запущенный API использует другой адрес, сначала остановите прежний лаунчер.

На компьютере автора проверочная PostgreSQL 18 находится в `/private/tmp/tipro-postgres18/bin`; при удалении временных бинарников установите PostgreSQL 18 и укажите TIPRO_PG_BIN. Данные остаются в `.runtime/pgdata`. Подробный быстрый старт — в [корневом README](../README.md).

## Windows и автоматическое окружение

Установите Node.js, Python 3.12+ и PostgreSQL 18. Из корня откройте `Запустить Tipro.bat` либо выполните `npm start`. Общая Node-обёртка создаёт `.venv` для текущей ОС, устанавливает `requirements.lock`, создаёт `.env`, если его ещё нет, и запускает общий `scripts/start.py`. В Windows используются `Scripts/python.exe`, `.exe` PostgreSQL, Windows-блокировка файла и остановка дерева собственных процессов; uvloop исключён для Windows.

PostgreSQL ищется в PATH, в `C:\Program Files\PostgreSQL\18\bin` или в `TIPRO_PG_BIN`. Новая изолированная БД создаётся внутри `.runtime/pgdata` автоматически, порт по умолчанию 55432. Существующие `.env` и данные не перезаписываются, seed не выполняется. При первом запуске нужен доступ к реестрам зависимостей.

`.venv` и `.runtime` должны оставаться в `.gitignore`. Это машинное окружение и локальные данные; для переноса предусмотрены зависимости, SQL-структура и миграции. `scripts/start.py` уже находится вне `.venv`, переносить его не требуется. Реальный Windows-запуск в этой среде не проверялся, проверка на macOS выполнена.

## Ручная установка вместо bootstrap

Обычному запуску достаточно `npm start`. Если нужно подготовить окружение вручную, выполняйте команды из корня.

macOS:

```sh
python3.12 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.lock
backend/.venv/bin/python backend/scripts/init_env.py --port 55432
```

Windows PowerShell:

```powershell
py -3.12 -m venv backend/.venv
.\backend\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock
.\backend\.venv\Scripts\python.exe backend/scripts/init_env.py --port 55432
```

`init_env.py` генерирует случайные секреты и не перезаписывает существующий файл. Для готового сервера PostgreSQL укажите его DATABASE_URL и доверенные адреса CORS_ORIGINS. Сам `.env`, дампы, окружение и рабочие данные в Git не добавляются.

Для HTTPS включите COOKIE_SECURE=true и настройте reverse proxy так, чтобы Vue и /api отдавались с одного origin. При ручном запуске без лаунчера укажите доступный телефону FRONTEND_URL и соответствующий CORS_ORIGINS. На телефоне localhost указывает на сам телефон.

## Дамп и существующая схема

`Users.sql` фактически является **PostgreSQL custom dump**, сигнатура `PGDMP`, формат 1.16, создан PostgreSQL 18.6. Это бинарный файл, его нельзя передавать в `psql -f`. Используйте PostgreSQL 18 `pg_restore`.

Перед восстановлением создайте новую пустую базу. Пример (пароль вводится средствами PostgreSQL, не указывается в командной строке):

```sh
createdb -h 127.0.0.1 -p 55432 -U tipro tipro_import
pg_restore --no-owner --no-acl --exit-on-error -h 127.0.0.1 -p 55432 -U tipro -d tipro_import /путь/Users.sql
```

Если база с данными уже существует, восстановление поверх неё не выполняйте. Сделайте резервную копию, проверьте структуру и применяйте миграции к существующей базе. Помощник `scripts/local_postgres.py --restore /путь/Users.sql` откажется восстанавливать дамп в непустую базу.

Пример предполагает уже работающий сервер на 127.0.0.1:55432; подставьте свой адрес и пользователя. После импорта укажите tipro_import в DATABASE_URL. Затем примените миграции (на обычном запуске их применяет npm start автоматически). Вручную на macOS:

```sh
cd backend
.venv/bin/alembic upgrade head
```

На Windows вместо `.venv/bin/alembic` используйте `.\.venv\Scripts\alembic.exe` из папки backend.

Миграции по порядку:

- `0001_legacy` проверяет четыре существующие таблицы; если база пустая, создаёт именно схему из дампа. При частичной/несовместимой схеме останавливается, ничего не подменяя. Схема без данных приведена в `schema/legacy.sql`.
- `0002_backend` добавляет поля валют, настроек, UTC, Argon2, приглашений, провайдера и идемпотентности; таблицы целей, сессий, webhook-событий и маркеров демозаполнения. Существующие записи сохраняются. Исходное поле `qr_links.mecrhant_id` сохранено; Python-атрибут называется `merchant_id`.
- `0003_sequences` поднимает отстающие identity-последовательности до существующих ID, чтобы новые вставки не сталкивались с данными дампа.
- `0004_qr_sessions` добавляет подпись по nonce/exp и снимок срока/nonce в платежах.
- `0005_permanent_qr` — промежуточный исторический формат общих QR; актуальные правила задаёт 0008.
- `0006_approval` добавляет approved_at и approved_by без изменения статусов существующих ресторанов. Публичная регистрация создаёт PENDING.
- `0007_employee_qr` добавляет used_at и ограничения для исторического v2: обязательный сотрудник, срок 24 часа и уникальный nonce. Прежние v1-коды сохраняются как отключённая история.
- `0008_receipt_payments` добавляет CREATED в enum платежей, таблицу audit_events, последовательность receipt_id_seq, ограничения v3-чеков и масок реквизитов. V2-коды отключаются без удаления записей; реквизиты заменяются масками последних четырёх цифр либо пустой строкой. При обновлении выпустите новые QR с суммой чека.

Исходные роли — enum `Position_enum`: `manager` → frontend `merchant`, `worker` → frontend `employee`, `visitor` не получает аккаунт для оплаты. Администратор платформы — дополнительный флаг `platform_admin` на записи менеджера. Сотрудники-аккаунты хранятся в исходной `employees`, новая независимая таблица пользователей не создаётся.

`employees.merchant_id` становится nullable для администратора платформы; `qr_links.employee_id` остаётся nullable только для истории; для новых v3-кодов ограничение БД требует сотрудника, чек, сумму и срок 24 часа. Поля `payments.amount` (сумма счёта) и `payments.tip` (чаевые) расширяются с `NUMERIC(10,2)` до `NUMERIC(20,4)`, без float. API-поле `amount` означает чаевые и соответствует `payments.tip`.

**В исходной схеме нет валюты.** Перед первой миграцией задайте `LEGACY_CURRENCY` соответственно исходным платежам. В выполненной локальной проверке использовано `RUB`. Миграция не конвертирует деньги. Новые платежи получают валюту своего QR; аналитика всегда разделяет валюты.

Пароли из исходного `password` преобразуются в Argon2 и переносятся в `password_hash`; открытое поле очищается. Логины сохраняются в нормализованном `auth_email`, в том числе старые логины без `@`; форма входа поддерживает email и логин. Дубли нормализованных логинов и распознанные сторонние форматы хешей останавливают миграцию с откатом для явного решения конфликта. Старые Argon2-хеши сохраняются.

Текстовый `payments.timestamp` сохранён. Распознаваемые ISO-даты преобразуются в `TIMESTAMPTZ`; даты без timezone трактуются как UTC. Нераспознаваемая дата остаётся в исходном поле, `created_at` будет NULL: такие платежи входят в общие итоги, но не получают вымышленную дату на графике.

Исходные QR имеют неизвестную старую схему подписи. Они сохраняются для истории с `token_version=legacy`, но не принимают новые платежи. Администратор выпускает новый серверный QR. Его криптографически случайный токен дополнительно проверяется HMAC, принадлежностью ресторану, активностью и сроком действия. Новые v3-коды привязаны к сотруднику и чеку, одноразовые и действуют 24 часа.

Разрушающие downgrade отключены. Для возврата используйте проверенную резервную копию в отдельной базе.

## Docker Compose

Требуется Docker с Compose. Docker в текущей среде отсутствует, поэтому запуск контейнеров здесь не проверен. Конфигурация подготовлена для PostgreSQL 18 и Python 3.12.

```sh
# Из корня, после генерации backend/.env
docker compose --env-file backend/.env up -d db
```

Для импорта в **пустую** контейнерную базу до запуска API:

```sh
docker compose --env-file backend/.env cp /Users/stepan/Downloads/Users.sql db:/tmp/Users.dump
docker compose --env-file backend/.env exec -T db sh -c 'pg_restore --no-owner --no-acl --exit-on-error -U "$POSTGRES_USER" -d "$POSTGRES_DB" /tmp/Users.dump'
```

Затем:

```sh
docker compose --env-file backend/.env up --build -d api
docker compose --env-file backend/.env exec api python -m app.seed
npm run dev
```

API автоматически применяет миграции. Данные PostgreSQL находятся в named volume `tipro_pg`; не используйте `down -v`, если их нужно сохранить. В Compose сервер PostgreSQL доступен локально на 5432, API — на 8000. `DATABASE_URL` внутри API-контейнера указывает на `db:5432`, независимо от адреса для запуска без Docker.

## Регистрация и одобрение ресторанов

Новые рестораны получают статус PENDING. Менеджер может получить ограниченную сессию для `/auth/me` и `/auth/logout`, чтобы видеть ожидание и войти повторно. Любой другой защищённый endpoint возвращает `MERCHANT_PENDING`, пока платформа не подтвердит ресторан. Публичный QR и создание оплаты также требуют ACTIVE.

`GET /api/admin/notifications` — пагинированные уведомления о PENDING-ресторанах. Они выводятся из сохранённых заявок, поэтому не теряются после перезапуска и доступны каждому администратору платформы. `POST /api/admin/restaurants/{id}/approve` — только для роли admin; блокировка строки делает повторное подтверждение идемпотентным. `approved_at` и `approved_by` сохраняют время и автора первого подтверждения. BLOCKED-ресторан этим действием не активируется.

Миграция `0006_approval` добавляет поля аудита без изменения статусов существующих ресторанов. SQL-снимок `schema/tipro.sql` обновлён. Демо-seed является явной доверенной серверной командой и создаёт активные деморестораны; публичная регистрация этим путём не пользуется.

Первый администратор создаётся из корня без включения публичной регистрации admin:

```sh
npm run create:admin -- --email admin@example.com --name "Администратор платформы"
```

## Проверка полного сценария

1. Зарегистрировать ресторан, дождаться подтверждения платформой и войти менеджером; добавить сотрудника. После сохранения появится одноразовое приглашение, действующее 7 дней. Просроченное приглашение можно перевыпустить из карточки. Зарегистрировать сотрудника по ссылке, добавить цель и выбрать текущую.
2. Войти менеджером и в «Настройки» выбрать язык гостевой страницы и предлагаемые проценты. Выбор валюты из интерфейса убран; новые QR и цели используют валюту ресторана. Интерфейс поддерживает русский, английский и китайский с переключателем и сохранением выбора в браузере. Язык ресторана задаёт язык гостевой страницы по умолчанию, если у гостя ещё нет своего выбора. Денежные значения в USD, EUR и CNY сохраняют два дробных знака; выбор валюты в интерфейсе не предлагается. Локальные методы оплаты не имитируют реальные банки: доступен только `demo`.
3. В «QR-код» / «QR-коды сотрудников» выбрать активного сотрудника, указать сумму и необязательный номер чека и создать одноразовый код на 24 часа. Код ведёт на существующий Vue-маршрут `/restaurant/{id}?qr={token}`. QR можно скачать в PNG; Python также генерирует PNG через защищённый `/api/qrs/{token}/image`.
4. Получатель и чек заданы кодом. Гость видит приветствие, выбирает процент или сумму чаевых, затем проверяет итог на отдельном экране. Создание платежа сохраняет CREATED и возвращает publicToken; провайдер ещё не вызывается. Отдельный POST confirm переводит его в PENDING и передаёт демопровайдеру сумму чека вместе с чаевыми. После этого сервер завершает обработку независимо от браузера; Vue проверяет статус.
5. Успех отражается в истории, аналитике и цели той же валюты. Отказ/отмена не увеличивают прогресс. Сотрудник получает только свои данные, менеджер — только свой ресторан, платформа — общий обзор. Разные валюты в базе не складываются и не конвертируются.
6. Скачивание CSV запрашивает экспорт у сервера с теми же ограничениями доступа.

В демонастройках гостевой страницы доступны успех, отказ и ожидание. Отмена доступна только до подтверждения (CREATED). Для намеренно `pending` платежа доступна проверка статуса; отмена из PENDING возвращает 409. Успешный результат содержит благодарность без переходов в кабинет. Серверный оператор может отправить настоящее подписанное демоподтверждение:

```sh
cd backend
.venv/bin/python scripts/send_demo_webhook.py PAYMENT_ID --status success
```

`PAYMENT_ID` — ID записи в истории. Подпись HMAC SHA-256 считается по `timestamp + '.' + raw_body`. Требуются `X-Webhook-Timestamp` и `X-Webhook-Signature`, допускается окно 5 минут. Повторное событие не зачисляет чаевые повторно; несовпадение общей суммы (`payments.amount + payments.tip`)/валюты отклоняется. Webhook не может завершить неподтверждённый CREATED-платёж. `WEBHOOK_SECRET` остаётся на сервере.

Идемпотентность: каждый запрос создания содержит `Idempotency-Key`. PostgreSQL advisory lock и unique constraint исключают дубли между конкурентными процессами; повтор с другими параметрами возвращает 409. Переходы статуса блокируют строку платежа, а увеличение цели атомарно. В JavaScript API-клиенте незавершённая попытка хранится в sessionStorage для повтора с тем же ключом; JWT там не хранится. Для действующего QR после перезагрузки гостевая страница восстанавливает незавершённую попытку. После использования или истечения QR повторное открытие самой платёжной ссылки отклоняется; статус завершённого платежа доступен по отдельному publicToken.

## Формат и жизненный цикл QR

Новый QR имеет `token_version=v3`. Менеджер передаёт обязательные `employeeId` и `billAmount`, необязательные `receiptNumber`, `currency`, `label`. Сотрудник должен быть активным работником его ресторана. Сервер назначает положительный receipt_id из последовательности; пустой номер заменяет этим ID. Пары (ресторан, receipt_id) и (ресторан, receipt_number) уникальны среди v3.

Токен URL: `{merchant_id}.{employee_id}.{receipt_id}.{nonce}.{exp}.{signature}`. URL остаётся `/restaurant/{merchant_id}?qr={token}`. Nonce — криптографически случайное 256-битное число в десятичной записи; exp — Unix timestamp UTC. Подпись — полный HMAC-SHA256 hex по строке `merchant_id|employee_id|receipt_id|nonce|exp`, ключ берётся из серверного JWT_SECRET. Более длинные nonce и подпись сохраняют защиту; они не сокращены до учебных 6/16 hex.

Срок задаётся сервером: ровно 24 часа от created_at. `expiresInDays` совместим только со значением 1; PATCH меняет только active. БД требует непустую сумму чека, сотрудника, receipt_id и срок, а также уникальный nonce. При чтении проверяются HMAC токена и подпись фактических полей записи. Публичный ответ содержит только назначенного сотрудника, чек и ресторан, без реквизитов и служебного аудита одобрения.

При создании платежа блокируется QR. Активная попытка CREATED или PENDING исключает вторую попытку с другим ключом (`QR_PAYMENT_PENDING`, 409). Повтор исходного Idempotency-Key возвращает тот же платёж (200); повтор с другими параметрами — 409. Перед обработкой и успехом проверяются подпись, срок, активность ресторана и сотрудника. Успех, used_at, отключение QR, зачисление цели и событие аудита выполняются в одной транзакции.

После одной успешной оплаты QR больше не принимает платежи; включить used/expired нельзя. После отказа либо отмены CREATED возможна новая попытка до истечения срока. По отдельному publicToken можно читать завершённый результат и после истечения QR. Прежние legacy/v1/v2-записи сохраняются, но требуют нового QR для оплаты. Seed создаёт v3-коды с демонстрационными чеками; исторические платежи не используют эти действующие коды.

## Создание, подтверждение и отмена платежа

`POST /api/public/qrs/{token}/payments`, заголовок `Idempotency-Key` (8–120 символов):

```json
{
  "employeeId": 1,
  "receiptId": 1101,
  "amount": "250.00",
  "currency": "RUB",
  "scenario": "success",
  "method": "demo"
}
```

ID, валюту и сумму чека берите из ответа QR, а не из примера. Вместо amount можно передать percent, но не оба поля. `amount` в этом API означает чаевые; ответ дополнительно содержит billAmount и amountTotal. Сумма чека хранится сервером и не принимается от гостя. ReceiptId и employeeId обязаны совпадать с QR.

- Сумма чека: > 0 и ≤ 1 000 000.
- Чаевые: ≥ 0 и ≤ 50% чека; процент: 0…50.
- Общая сумма: ≤ 2 000 000; провайдер и webhook работают с ней, цель — только с чаевыми.
- Расчёт — Decimal, ROUND_HALF_UP по дробности валюты; результат ограничен 50% с округлением предела вниз до минимальной денежной единицы.

Создание возвращает CREATED (201), без обращения к провайдеру. `POST /api/public/payments/{publicToken}/confirm` подтверждает оплату, создаёт один provider intent и переводит в PENDING. Повтор confirm не создаёт новое списание. Серверный worker или подписанный webhook переводит PENDING в SUCCESS/DECLINED. Таймаут остаётся PENDING до результата или окончания срока QR, после которого платёж отклоняется с QR_EXPIRED.

`POST /api/public/payments/{publicToken}/cancel` разрешён только из CREATED; повтор уже выполненной отмены возвращает CANCELED. Отмена PENDING, SUCCESS или DECLINED возвращает CANCEL_NOT_ALLOWED (409). API также сохраняет совместимость с демосценарием cancelled: confirm такого CREATED-платежа отменяет его до обращения к провайдеру; интерфейс предлагает отмену отдельной кнопкой.

`GET /api/public/payments/{publicToken}` возвращает текущий статус. Пока ссылка действительна, Vue восстанавливает незавершённую попытку из sessionStorage и показывает подтверждение CREATED или проверку PENDING. После использования/истечения сам QR отклоняется; отдельный publicToken остаётся доступен.

## Ошибки и ограничения

ApiError возвращает `{message, code, retryable}`. Основные причины:

| Ситуация | Код | HTTP |
| --- | --- | --- |
| Подпись или содержимое QR неверны | INVALID_QR | 422 |
| QR использован | QR_USED | 409 |
| QR истёк | QR_EXPIRED | 410 |
| Ресторан заблокирован | MERCHANT_BLOCKED | 403 |
| Чек не соответствует QR | RECEIPT_MISMATCH | 422 |
| Сумма вне допустимых границ | AMOUNT_OUT_OF_RANGE | 422 |
| Чаевые превышают предел | TIP_OUT_OF_RANGE | 422 |
| Отмена после подтверждения | CANCEL_NOT_ALLOWED | 409 |
| Другая активная попытка по QR | QR_PAYMENT_PENDING | 409 |
| Частота запросов превышена | RATE_LIMIT | 429 |

При отказе демопровайдера платёж имеет status=declined и errorCode=CARD_DECLINED. При обнаружении истечения или блокировки во время подтверждения/завершения API возвращает состояние отклонённого платежа с errorCode; таблица HTTP относится к отклонению публичного QR-запроса до создания платежа. Ошибки формата Pydantic возвращают VALIDATION (422), ошибки денежной точности — VALIDATION (400).

Лимиты в одном процессе: до 60 запросов входа/регистрации за 5 минут на IP и 300 публичных запросов в минуту на IP. В нескольких процессах для общего лимита нужен внешний rate limiter. JWT и платёжные ссылки не пишутся в access log.

## Блокировки, аудит и реквизиты

Только платформа может вызывать `POST /api/admin/restaurants/{id}/block` и `/unblock`. Блокировка немедленно закрывает доступ менеджеру/сотрудникам и новым платежам; перед успехом начатого платежа статус проверяется повторно. Выход из аккаунта остаётся доступен. Разблокировка возвращает ACTIVE при сохранённом approved_at, иначе PENDING для повторного одобрения.

`audit_events` хранит event_id, payment_id, qr_id, merchant_id, action, from_status, to_status, amount_total, actor и at. Новые события создаются атомарно с изменениями, повторные подтверждения не дублируют их. Доступ: `GET /api/admin/audit?payment_id=...&offset=0&limit=100`; платформа видит все события, менеджер — только свой ресторан, сотруднику/гостю доступ закрыт. Исторические события задним числом не выдумываются.

Сотруднику через API можно передать paymentDetails только пустым либо в формате `****1234`. Ограничение продублировано в БД; при миграции полные прежние значения заменяются маской. Поле выдаётся в приватной карточке, публичному гостю не передаётся. PAN/CVV и полные реквизиты не собираются.

## Дополнительная статистика

`GET /api/analytics` сохраняет прежние totals/series/byEmployee и ограничения доступа. В totals добавлены avgTipPct (среднее `tip / amount × 100` успешных платежей с ненулевым чеком), successRate (SUCCESS / все платежи), topDay (день максимальной суммы успешных чаевых, при равенстве — более ранний). Average — средние чаевые на успешный платёж. В series добавлен avgTipPct; дни и topDay определяются в запрошенной timezone. Валюты не смешиваются.

CSV содержит ID, дату UTC, сотрудника, сумму чека, итог, чаевые, валюту и статус. Экспорт соблюдает тот же scope и календарный фильтр, что история.

## Тестирование

```sh
npm run test:backend
npm run build
npm run check:api
```

`pytest` создаёт отдельную случайную базу с префиксом `tipro_test_` и удаляет только её. Нужны работающий PostgreSQL и право CREATEDB у тестового пользователя. Можно задать `TEST_DATABASE_URL` с адресом отдельного тестового сервера. SQLite не используется. Тесты проверяют миграции, Argon2/JWT/выход, приглашения, границы ресторанов и сотрудников, QR, проценты, валюты, конкурентные идемпотентные запросы, webhook и CSV. Дополнительные приёмочные проверки в tests/test_receipt_payments.py покрывают CREATED/confirm/cancel, полную подпись QR, пределы и округление, аудит, маски и блокировку во время оплаты.

`check:api` требует запущенный API и seed; при отсутствии пригодного кода создаёт новый QR, привязанный к тестовому сотруднику, использует **тот же JavaScript-адаптер, что Vue**, выполняет демооплату 12.50 THB и проверяет её в БД через API, цели сотрудника, статистику менеджера и CSV. Он добавляет новую демоцель и платёж тестовому сотруднику. `npm test` проверяет даты графика, переводы, ожидание одобрения, подготовку окружения и сохранённый старый mock; приложение на него больше не переключается.

## Архитектура и API

- `app/models/`: исходные четыре таблицы и дополнительные модели.
- `app/core/`: JWT, Argon2, роли, Decimal-валидация и ошибки.
- `app/routers/`: auth, сотрудники/рестораны/цели, QR, платежи, аналитика.
- `app/services/providers.py`: асинхронный контракт провайдера, серверный demo-адаптер.
- `app/services/payments.py`: идемпотентность и атомарные переходы.
- `app/services/audit.py`: запись событий платежей в текущую транзакцию.
- `app/services/worker.py`: серверное подтверждение demo; пригодно для нескольких процессов за счёт `SKIP LOCKED`.
- `alembic/`: принятие существующей схемы и добавочные миграции.

Основные пути доступны в Swagger. Списки `/employees`, `/restaurants`, `/qrs`, `/payments` имеют `offset` и `limit<=100`. Vue-адаптер сейчас собирает страницы в списки для существующих экранов; серверная пагинация доступна для дальнейшей оптимизации больших объёмов. `/analytics` фильтрует `start`, `end` (включительно в запрошенном часовом поясе), `currency`, `employee_id`, `merchant_id`; интервалы `day`, `week`, `month`. Итоги возвращаются массивом по валютам, без фиктивной конвертации. JSON передаёт Decimal как строки; JS преобразует их только для отображения.

JWT принимается в `Authorization: Bearer` и HttpOnly cookie. В JS bearer находится в памяти; после перезагрузки работает серверная cookie-сессия. Выход отзывает запись сессии. CORS ограничен настройками, изменяющие запросы дополнительно проверяют Origin, вход ограничивает частоту попыток. Доступ к данным проверяется сервером, а не полями роли из JWT/фронтенда. Токены и платёжные ссылки не пишутся в access log.

Для реального провайдера реализуйте асинхронный контракт `PaymentProvider`, зарегистрируйте адаптер и его платёжный метод, добавьте проверку его webhook. Бизнес-переходы и учёт целей уже вынесены отдельно. Live-провайдер, банковские реквизиты, реальные списания, валютная конвертация в этот MVP не входят. Интерфейс переведён на русский, английский и китайский; авторские названия и тексты не переводятся автоматически.

## Даты графиков и фильтров

Моменты платежей хранятся в UTC и при исправлении графика не переписываются. Vue отправляет часовой пояс браузера в query-параметре `timezone` для аналитики, истории и экспорта. Без параметра API использует UTC. Имя проверяется по `pg_timezone_names`, неизвестное имя возвращает INVALID_TIMEZONE.

Сервер группирует дни, недели и месяцы в указанной зоне независимо от TimeZone сессии PostgreSQL. В `series` поля `date` и `period` — календарные ключи YYYY-MM-DD, а `timezone` в ответе задаёт зону этих ключей. График использует их напрямую, без повторной конвертации в UTC. Если зона серверных агрегатов отличается, график пересчитывает дни по исходным платежам.

Границы фильтра вычисляются от полуночи начала дня до полуночи следующего дня в той же зоне. Это учитывает 23- и 25-часовые дни при переводе часов. Строки времени в CSV остаются UTC, а отбор записей соответствует выбранному локальному календарному дню.
