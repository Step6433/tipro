# Tipro backend

FastAPI + PostgreSQL 18 + SQLAlchemy 2 asyncpg. Существующий Vue-фронтенд использует `/api`; Swagger: http://127.0.0.1:8000/docs. Настоящих списаний нет.

## Быстрый запуск в текущей рабочей среде

Уже создано окружение `.venv`, сгенерирован локальный `.env` с секретами и запущена отдельная PostgreSQL на `127.0.0.1:55432`. Исходный дамп из `/Users/stepan/Downloads/Users.sql` восстановлен в новую базу `tipro`, применены миграции. По запросу пользователя рабочая база возвращена к исходным записям дампа без дополнительных демоданных: 20 ресторанов, 60 сотрудников, 100 платежей и 100 исторических QR. Цели, сессии и маркеры seed пусты. Локальная резервная копия состояния до восстановления находится в `.runtime/backups` и не попадает в Git. Другие базы не изменялись.

В Finder дважды нажмите `Запустить Tipro.command` в корне проекта — он запустит базу, миграции, FastAPI и Vue и откроет сайт. Либо выполните из корня одну команду:

```sh
npm start
```

Для остановки используйте Ctrl+C в окне запуска. Лаунчер завершает только собственные серверы, PostgreSQL продолжает работать. Уже запущенные серверы используются повторно. Seed при запуске не выполняется, существующие настройки и данные не перезаписываются. Лаунчер требует уже установленных Python/Node-зависимостей и `.env`; для нового компьютера сначала выполните установку ниже. `TIPRO_PG_BIN` позволяет указать свою папку с бинарниками PostgreSQL. `npm start -- --no-open` запускает без открытия браузера. При старте лаунчер определяет IPv4 Mac в локальной сети, передаёт его в `FRONTEND_URL` и CORS, а Vue слушает сетевые подключения. Телефон и Mac должны быть в одной Wi-Fi сети. Для явного выбора адреса используйте `TIPRO_LAN_HOST=192.168.2.147 npm start`. Файл `.env` при этом не переписывается; API и БД доступны только локально, телефон использует `/api` через Vue-прокси. Ранее сохранённые QR с localhost скачайте заново. Если ранее запущенный API использует другой адрес QR, сначала остановите прежний лаунчер через Ctrl+C.

Для раздельного запуска по-прежнему доступны `npm run dev:api` и `npm run dev` в двух терминалах.

Если временная PostgreSQL остановлена, её можно запустить снова из корня:

```sh
backend/.venv/bin/python backend/scripts/local_postgres.py --bin-dir /private/tmp/tipro-postgres18/bin
```

Эти бинарники PostgreSQL 18 собраны из официальных исходников во временной папке для проверки на этом Intel Mac. Системная служба не установлена. После очистки временной папки используйте установленную PostgreSQL 18 (`--bin-dir /путь/к/bin`) либо Docker, описанный ниже. Данные находятся в `backend/.runtime/pgdata`, а не во временной папке с бинарниками. Не удаляйте этот каталог без резервной копии.

## Установка с нуля

Python 3.12+ и PostgreSQL 18. Из корня проекта:

```sh
python3.12 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.lock
backend/.venv/bin/python backend/scripts/init_env.py
```

`init_env.py` создаёт `backend/.env` с правами 0600 и случайными паролями/секретами. Существующий файл не перезаписывается. Пример параметров — `.env.example`. Укажите свой `DATABASE_URL=postgresql+asyncpg://...` и доверенные адреса в `CORS_ORIGINS`. Для локальной отдельной PostgreSQL на другом порту: `init_env.py --port 55432` до создания `.env`.

Секреты, дамп, виртуальное окружение и файлы БД исключены из Git. Не добавляйте их в коммит. Для HTTPS включите `COOKIE_SECURE=true`; reverse proxy должен отдавать `/api` и Vue с одного origin. При изменении сетевого адреса фронтенда настройте `FRONTEND_URL` и соответствующий `CORS_ORIGINS`, чтобы QR содержал доступный телефону URL. Один `localhost` на другом устройстве не указывает на компьютер с сервером.

## Дамп и существующая схема

`Users.sql` фактически является **PostgreSQL custom dump**, сигнатура `PGDMP`, формат 1.16, создан PostgreSQL 18.6. Это бинарный файл, его нельзя передавать в `psql -f`. Используйте PostgreSQL 18 `pg_restore`.

Перед восстановлением создайте новую пустую базу. Пример (пароль вводится средствами PostgreSQL, не указывается в командной строке):

```sh
createdb -h localhost -U tipro tipro
pg_restore --no-owner --no-acl --exit-on-error -h localhost -U tipro -d tipro /Users/stepan/Downloads/Users.sql
```

Если база с данными уже существует, восстановление поверх неё не выполняйте. Сделайте резервную копию, проверьте структуру и применяйте миграции к существующей базе. Помощник `scripts/local_postgres.py --restore /путь/Users.sql` откажется восстанавливать дамп в непустую базу.

После восстановления или для новой пустой базы:

```sh
cd backend
.venv/bin/alembic upgrade head
```

Миграции:

- `0001_legacy` проверяет четыре существующие таблицы; если база пустая, создаёт именно схему из дампа. При частичной/несовместимой схеме останавливается, ничего не подменяя. Схема без данных приведена в `schema/legacy.sql`.
- `0002_backend` добавляет поля валют, настроек, UTC, Argon2, приглашений, провайдера и идемпотентности; таблицы целей, сессий, webhook-событий и маркеров демозаполнения. Существующие записи сохраняются. Исходное поле `qr_links.mecrhant_id` сохранено; Python-атрибут называется `merchant_id`.
- `0004_qr_sessions` включает подпись по `nonce` и `exp`, переводит `exp` активных серверных QR в Unix timestamp и добавляет снимок nonce/срока сессии в платежи. Строки QR сохраняются, ссылки старого формата нужно заново скачать из кабинета менеджера.
- `0003_sequences` только поднимает отстающие identity-последовательности до существующих ID. В исходном дампе последовательности отставали от записей; без исправления новые вставки сталкивались с первичными ключами.

Исходные роли — enum `Position_enum`: `manager` → frontend `merchant`, `worker` → frontend `employee`, `visitor` не получает аккаунт для оплаты. Администратор платформы — дополнительный флаг `platform_admin` на записи менеджера. Сотрудники-аккаунты хранятся в исходной `employees`, новая независимая таблица пользователей не создаётся.

`employees.merchant_id` становится nullable для администратора платформы; `qr_links.employee_id` — для QR всего ресторана. Поля `payments.amount` (сумма счёта) и `payments.tip` (чаевые) расширяются с `NUMERIC(10,2)` до `NUMERIC(20,4)`, без float. API-поле `amount` означает чаевые и соответствует `payments.tip`.

**В исходной схеме нет валюты.** Перед первой миграцией задайте `LEGACY_CURRENCY` соответственно исходным платежам. В выполненной локальной проверке использовано `RUB`. Миграция не конвертирует деньги. Новые платежи получают валюту своего QR; аналитика всегда разделяет валюты.

Пароли из исходного `password` преобразуются в Argon2 и переносятся в `password_hash`; открытое поле очищается. Логины сохраняются в нормализованном `auth_email`, в том числе старые логины без `@`; форма входа поддерживает email и логин. Дубли нормализованных логинов и распознанные сторонние форматы хешей останавливают миграцию с откатом для явного решения конфликта. Старые Argon2-хеши сохраняются.

Текстовый `payments.timestamp` сохранён. Распознаваемые ISO-даты преобразуются в `TIMESTAMPTZ`; даты без timezone трактуются как UTC. Нераспознаваемая дата остаётся в исходном поле, `created_at` будет NULL: такие платежи входят в общие итоги, но не получают вымышленную дату на графике.

Исходные QR имеют неизвестную старую схему подписи. Они сохраняются для истории с `token_version=legacy`, но не принимают новые платежи. Администратор выпускает новый серверный QR. Его криптографически случайный токен дополнительно проверяется HMAC, принадлежностью ресторану, активностью и сроком действия. Новые коды постоянные; временный срок доступен только при явном expiresInDays.

Разрушающие downgrade отключены. Для возврата используйте проверенную резервную копию в отдельной базе.

## Docker Compose

Требуется Docker с Compose. Docker в текущей среде отсутствует, поэтому запуск контейнеров здесь не проверен. Конфигурация подготовлена для PostgreSQL 18 и Python 3.12.

```sh
# Из корня, после генерации backend/.env
docker compose --env-file backend/.env up -d db
```

Для импорта в **пустую** контейнерную базу до запуска API:

```sh
docker compose --env-file backend/.env cp /Users/stepan/Downloads/Users.sql db:/tmp/Users.dump
docker compose --env-file backend/.env exec -T db sh -c 'pg_restore --no-owner --no-acl --exit-on-error -U "$POSTGRES_USER" -d "$POSTGRES_DB" /tmp/Users.dump'
```

Затем:

```sh
docker compose --env-file backend/.env up --build -d api
docker compose --env-file backend/.env exec api python -m app.seed
npm run dev
```

API автоматически применяет миграции. Данные PostgreSQL находятся в named volume `tipro_pg`; не используйте `down -v`, если их нужно сохранить. В Compose сервер PostgreSQL доступен локально на 5432, API — на 8000. `DATABASE_URL` внутри API-контейнера указывает на `db:5432`, независимо от адреса для запуска без Docker.

## Демоданные и аккаунты

После восстановления исходной базы перечисленных ниже демоаккаунтов в рабочей базе нет. Seed запускается только вручную; обычный запуск приложения его не выполняет.

Заполнение запускается отдельно и повторно не изменяет существующие записи или пароли:

```sh
cd backend
.venv/bin/python -m app.seed
```

Нужен `DEMO_PASSWORD` длиной от 12 символов в `.env`; генератор окружения уже создал случайное значение. Пароли не печатаются в лог. Три демонстрационных ресторана работают в THB, SGD и VND, добавляются менеджеры, официанты, цели, QR и 30 дней платежей разных статусов. Исходные записи дампа не заменяются.

| Роль | Логин |
| --- | --- |
| Администратор платформы | `admin@tipro.example.com` |
| Менеджер Бангкока, THB | `manager1@tipro.example.com` |
| Менеджер Сингапура, SGD | `manager2@tipro.example.com` |
| Менеджер Ханоя, VND | `manager3@tipro.example.com` |
| Сотрудники Бангкока | `worker11@tipro.example.com`, `worker12@tipro.example.com` |
| Сотрудники Сингапура | `worker21@tipro.example.com`, `worker22@tipro.example.com` |
| Сотрудники Ханоя | `worker31@tipro.example.com`, `worker32@tipro.example.com` |

Пароль этих новых демоаккаунтов — текущее значение `DEMO_PASSWORD` при первом запуске seed. Прежний `Demo12345` от localStorage-мока не создаёт серверный доступ. Смена переменной после seed не перезаписывает существующие пароли.

Самостоятельная регистрация администратора платформы закрыта по умолчанию. Создать отдельный аккаунт без seed:

```sh
cd backend
.venv/bin/python -m app.cli create-admin --email admin@example.com --name 'Администратор'
```

Команда запросит пароль без отображения ввода. Для контролируемой демосреды можно явно включить `ALLOW_ADMIN_REGISTRATION=true`; в production не включайте.

## Проверка полного сценария

1. Войти менеджером; добавить сотрудника. После сохранения появится одноразовое приглашение, действующее 7 дней. Просроченное приглашение можно перевыпустить из карточки. Зарегистрировать сотрудника по ссылке, добавить цель и выбрать текущую.
2. Войти менеджером и в «Настройки» выбрать язык гостевой страницы и предлагаемые проценты. Выбор валюты из интерфейса убран; новые QR и цели используют валюту ресторана. Интерфейс поддерживает русский, английский и китайский с переключателем и сохранением выбора в браузере. Язык ресторана задаёт язык гостевой страницы по умолчанию, если у гостя ещё нет своего выбора. USD, EUR и CNY доступны вместе с прежними валютами, все три имеют 2 дробных знака. Локальные методы оплаты не имитируют реальные банки: доступен только `demo`.
3. В «QR-код» создать постоянный код ресторана. Код ведёт на существующий Vue-маршрут `/restaurant/{id}?qr={token}`. QR можно скачать в PNG; Python также генерирует PNG через защищённый `/api/qrs/{token}/image`.
4. Гость выбирает сотрудника и фиксированную сумму. `POST` создаёт в PostgreSQL `PENDING`, возвращает случайный токен просмотра статуса. Серверный демопровайдер подтверждает исход независимо от браузера; Vue опрашивает статус.
5. Успех отражается в истории, аналитике и цели той же валюты. Отказ/отмена не увеличивают прогресс. Сотрудник получает только свои данные, менеджер — только свой ресторан, платформа — общий обзор. Разные валюты в базе не складываются и не конвертируются.
6. Скачивание CSV запрашивает экспорт у сервера с теми же ограничениями доступа.

В демонастройках гостевой страницы доступны успех, отказ, отмена и ожидание. Для намеренно `pending` платежа можно нажать «Проверить статус» или «Отменить». Серверный оператор может отправить настоящее подписанное демоподтверждение:

```sh
cd backend
.venv/bin/python scripts/send_demo_webhook.py PAYMENT_ID --status success
```

`PAYMENT_ID` — ID записи в истории. Подпись HMAC SHA-256 считается по `timestamp + '.' + raw_body`. Требуются `X-Webhook-Timestamp` и `X-Webhook-Signature`, допускается окно 5 минут. Повторное событие не зачисляет чаевые повторно; несовпадение суммы/валюты отклоняется. `WEBHOOK_SECRET` остаётся на сервере.

Идемпотентность: каждый запрос создания содержит `Idempotency-Key`. PostgreSQL advisory lock и unique constraint исключают дубли между конкурентными процессами; повтор с другими параметрами возвращает 409. Переходы статуса блокируют строку платежа, а увеличение цели атомарно. В JavaScript API-клиенте незавершённая попытка хранится в sessionStorage для повтора с тем же ключом; JWT там не хранится. После перезагрузки гостевая страница восстанавливает статус незавершённой попытки.

## Формат и жизненный цикл QR

Постоянная ссылка содержит `qr={nonce}.0.{sign}`. Существующие поля `nonce`, `exp`, `signature` сохранены; API называет подпись `sign`. `nonce` — случайное 256-битное число, `exp=0` означает отсутствие срока, `sign = HMAC-SHA256(secret, "qr:" + nonce + ":" + exp)`. Сервер проверяет подпись, совпадение с БД и активность ресторана/кода. Менеджер может отключить код вручную. После оплаты nonce и подпись **не меняются** — одним QR пользуются разные гости.

Новые QR создаются без номера и суммы чека; гость выбирает фиксированную сумму чаевых. Создание и печать чеков убраны из интерфейса. После успеха показана только благодарность без кнопок и ссылок продолжения. PNG можно скачать в кабинете, а также через `/api/qrs/{token}/image`.

Миграция `0005_permanent_qr` переводит существующие серверные QR в постоянный формат. Один раз скачайте PNG заново после перехода; затем регулярное обновление не требуется. Строки, история платежей и старые реквизиты чеков остаются в БД. Старые legacy-QR из дампа остаются историческими. Совместимый API позволяет явно выпустить временный QR через `expiresInDays`, но интерфейс этого не предлагает.

Постоянный QR не продлевает незавершённый платёж бесконечно: отдельная платёжная сессия действует 30 минут. Для временного QR сессия ограничена его exp. Просроченное подтверждение отклоняется с `QR_EXPIRED`. Идемпотентность и атомарное зачисление в цель сохраняются. После завершения одной сессии следующий гость открывает ту же постоянную ссылку и создаёт свой платёж.

Постоянство токена не закрепляет IP компьютера: при смене Wi-Fi/IP сохранённый сетевой URL требует обновления. Для печати надолго используйте постоянный IP в локальной сети или домен при размещении приложения на сервере.

## Тестирование

```sh
npm run test:backend
npm run build
npm run check:api
```

`pytest` создаёт отдельную случайную базу с префиксом `tipro_test_` и удаляет только её. Нужны работающий PostgreSQL и право CREATEDB у тестового пользователя. Можно задать `TEST_DATABASE_URL` с адресом отдельного тестового сервера. SQLite не используется. Тесты проверяют миграции, Argon2/JWT/выход, приглашения, границы ресторанов и сотрудников, QR, проценты, валюты, конкурентные идемпотентные запросы, webhook и CSV.

`check:api` требует запущенный API и seed; использует **тот же JavaScript-адаптер, что Vue**, выполняет демооплату 12.50 THB и проверяет её в БД через API, цели сотрудника, статистику менеджера и CSV. Он добавляет новую демоцель и платёж тестовому сотруднику. Исторический `npm test` проверяет сохранённый старый mock отдельно; приложение на него больше не переключается.

## Архитектура и API

- `app/models/`: исходные четыре таблицы и дополнительные модели.
- `app/core/`: JWT, Argon2, роли, Decimal-валидация и ошибки.
- `app/routers/`: auth, сотрудники/рестораны/цели, QR, платежи, аналитика.
- `app/services/providers.py`: асинхронный контракт провайдера, серверный demo-адаптер.
- `app/services/payments.py`: идемпотентность и атомарные переходы.
- `app/services/worker.py`: серверное подтверждение demo; пригодно для нескольких процессов за счёт `SKIP LOCKED`.
- `alembic/`: принятие существующей схемы и добавочные миграции.

Основные пути доступны в Swagger. Списки `/employees`, `/restaurants`, `/qrs`, `/payments` имеют `offset` и `limit<=100`. Vue-адаптер сейчас собирает страницы в списки для существующих экранов; серверная пагинация доступна для дальнейшей оптимизации больших объёмов. `/analytics` фильтрует `start`, `end` (включительно, UTC), `currency`, `employee_id`, `merchant_id`; интервалы `day`, `week`, `month`. Итоги возвращаются массивом по валютам, без фиктивной конвертации. JSON передаёт Decimal как строки; JS преобразует их только для отображения.

JWT принимается в `Authorization: Bearer` и HttpOnly cookie. В JS bearer находится в памяти; после перезагрузки работает серверная cookie-сессия. Выход отзывает запись сессии. CORS ограничен настройками, изменяющие запросы дополнительно проверяют Origin, вход ограничивает частоту попыток. Доступ к данным проверяется сервером, а не полями роли из JWT/фронтенда. Токены и платёжные ссылки не пишутся в access log.

Для реального провайдера реализуйте асинхронный контракт `PaymentProvider`, зарегистрируйте адаптер и его платёжный метод, добавьте проверку его webhook. Бизнес-переходы и учёт целей уже вынесены отдельно. Live-провайдер, банковские реквизиты, реальные списания, валютная конвертация в этот MVP не входят. Интерфейс переведён на русский, английский и китайский; авторские названия и тексты не переводятся автоматически.

## SQL-структура в проекте

Полный актуальный SQL-снимок находится в `schema/tipro.sql`, инструкция импорта — [schema/README.md](schema/README.md). Он содержит структуру и версию миграций, без пользователей, паролей и платежей. Локальные рабочие записи находятся в `.runtime/pgdata` и исключены из Git. Обновление снимка из корня: `npm run db:schema`.
