# Tipro — онлайн-чаевые

Vue 3 + FastAPI + PostgreSQL. Менеджер ресторана добавляет сотрудников и выпускает QR для конкретного чека и сотрудника. Гость сканирует код, проверяет сумму чека, выбирает чаевые и подтверждает демооплату без регистрации. Оплата увеличивает личную статистику сотрудника и прогресс его текущей цели. Реальные деньги не списываются.

## Запуск

На компьютере должны быть установлены Node.js с npm, Python 3.12+ и PostgreSQL 18. При первом запуске нужен интернет для установки зависимостей.

- **macOS:** дважды нажмите `Запустить Tipro.command` в Finder.
- **Windows:** дважды нажмите `Запустить Tipro.bat`.
- **Терминал на обеих ОС:** откройте корень проекта и выполните:

```sh
npm start
```

Лаунчер создаёт локальную `.venv`, устанавливает Python- и Vue-зависимости, генерирует `backend/.env`, если его ещё нет, запускает отдельную PostgreSQL, применяет миграции и поднимает FastAPI и Vue. На новом компьютере создаётся **пустая** база на порту 55432. Существующие `.env` и данные не перезаписываются. Демоаккаунты автоматически не создаются.

Дождитесь сообщения «Tipro готов». Браузер откроется автоматически; локальный адрес — обычно http://localhost:5173, документация API — http://127.0.0.1:8000/docs. Для запуска без браузера:

```sh
npm start -- --no-open
```

Оставьте окно запуска открытым. **Ctrl+C** завершает только серверы, запущенные этим окном. PostgreSQL и ранее запущенные серверы продолжают работать. Для раздельного запуска доступны `npm run dev:api` и `npm run dev`.

`.venv` остаётся в `.gitignore`: это окружение конкретной ОС, которое создаётся заново. Скрипты `scripts/run-python.mjs` и `scripts/start.py` находятся в Git вне `.venv`. Windows-ветка подготовлена; реальный запуск проверен на macOS, Windows в этой среде не проверялся.

### Если PostgreSQL не найден

Укажите папку с бинарниками PostgreSQL 18. PowerShell:

```powershell
$env:TIPRO_PG_BIN = 'C:\Program Files\PostgreSQL\18\bin'
npm start
```

macOS:

```sh
TIPRO_PG_BIN=/путь/к/postgresql/bin npm start
```

На компьютере автора проверочная PostgreSQL собрана в `/private/tmp/tipro-postgres18/bin`; временные бинарники могут быть удалены ОС. Данные находятся отдельно — в `backend/.runtime/pgdata`.

## Первый администратор и подтверждение ресторана

В новой базе нет готового администратора и общего пароля. После запуска приложения откройте второй терминал в корне проекта:

```sh
npm run create:admin -- --email admin@example.com --name "Администратор платформы"
```

Команда попросит задать пароль длиной от 12 символов. Войдите на сайте с указанным email и этим паролем. Самостоятельная регистрация администратора платформы по умолчанию закрыта; пароль хранится только как Argon2-хеш.

Новый ресторан проходит следующий путь:

1. Менеджер регистрирует ресторан. Запись сохраняется со статусом **PENDING**.
2. Менеджер видит страницу ожидания. До одобрения ему недоступны сотрудники, QR, настройки, платежи и статистика. Ограничения проверяет сервер.
3. В кабинете администратора платформы появляется заявка и счётчик уведомлений. Список обновляется каждые 10 секунд.
4. Администратор нажимает **«Подтвердить ресторан»**. Статус становится ACTIVE; сохраняются время и автор одобрения.
5. Страница ожидания менеджера проверяет статус каждые 5 секунд и открывает кабинет после подтверждения.

Существующие рестораны сохраняют свои статусы. Мерчант и сотрудник не могут подтвердить ресторан собственным токеном.

## Команда, цели и оплата

1. Менеджер открывает «Команда», добавляет сотрудника и передаёт ему одноразовое приглашение. **Приглашение для регистрации действует 7 дней и не является платёжным QR.**
2. Сотрудник регистрируется по приглашению и при желании добавляет личную цель. Он видит только свои платежи, статистику и цели.
3. Менеджер открывает «QR-код», выбирает активного сотрудника, указывает сумму чека и при необходимости его номер. Если номер пустой, сервер создаёт его автоматически. Для одного номера чека в ресторане допускается один QR нового формата. PNG можно скачать и разместить на чеке; печать кассового чека приложение не выполняет.
4. Гость сканирует QR и видит ресторан, официанта и сумму чека. Затем выбирает процент (0%, 5%, 10%, 15%, 20% и дополнительные значения ресторана) или свою сумму и переходит к подтверждению. На отдельном экране показаны чек, чаевые и общий итог. До нажатия «Подтвердить оплату» платёж можно отменить.
5. После подтверждения сервер отправляет в демообработку общую сумму чека и чаевых. Отмена во время обработки запрещена; статус можно проверить. Успех увеличивает статистику и цель той же валюты. Гость видит благодарность без кнопок продолжения на платформе.

Менеджер видит данные только своего ресторана, администратор платформы — общий обзор. В кабинете платформы можно выбрать ресторан и заблокировать или разблокировать его. Блокировка закрывает кабинет ресторана и новые оплаты; также проверяется перед успешным завершением уже начатой оплаты. Разблокировка возвращает одобренный ресторан в ACTIVE, а ресторан без сохранённого одобрения — в PENDING. В открытом кабинете менеджера/сотрудника данные обновляются каждые 5 секунд.

## Правила QR

- Каждый новый QR формата v3 связан с рестораном, одним `employee_id` и уникальным `receipt_id`. HMAC-SHA256 защищает ресторан, сотрудника, чек, nonce и срок действия.
- Срок действия — **ровно 24 часа** от создания. Сервер проверяет срок и при начале оплаты, и при подтверждении.
- После **одной успешной оплаты** QR получает `used_at` и отключается. Для следующего платежа нужен новый код.
- Две одновременные попытки не создают два платежа провайдера. Повтор того же Idempotency-Key возвращает прежний платёж без повторного зачисления.
- Отказ или отмена не увеличивают чаевые; до истечения срока можно попробовать снова. Использованный или просроченный QR нельзя включить повторно.
- Коды прежних форматов сохранены в истории, но не принимают оплату. Миграция `0008_receipt_payments` отключает v2-коды без привязки к чеку. Создайте новые QR с сотрудником и суммой чека.

В демонастройках оплаты доступны успех, отказ и ожидание. Отмена — отдельное действие до подтверждения, а не сценарий отказа шлюза. Реальные банки и касса не подключены. Подробности подписей и webhook — в [документации бэкенда](backend/README.md).

## Суммы, статусы и безопасность

Сумма чека должна быть больше нуля и не превышать 1 000 000. Чаевые — от нуля до 50% чека, общий итог — не более 2 000 000. Ограничения проверяет сервер. Дробные знаки соответствуют валюте; округление процента не может увеличить чаевые выше 50%.

Платёж проходит `CREATED → PENDING → SUCCESS / DECLINED`. `CREATED` означает, что клиент ещё проверяет итог: провайдер не вызывается, разрешён переход в `CANCELED`. После подтверждения (`PENDING`) и после успеха отмена возвращает `CANCEL_NOT_ALLOWED` (409). Пока QR не использован и не истёк, после отказа/отмены можно создать новую попытку.

В карточке сотрудника можно указать только маску реквизитов вида `****1234`. Полные реквизиты не принимаются; миграция заменяет прежние значения масками. Публичная страница их не выдаёт. Журнал `audit_events` хранит создание и переходы платежей, одобрение и блокировки ресторанов. API журнала доступен платформе и менеджеру своего ресторана.

Статистика дополнена средним процентом чаевых, долей успешных платежей и лучшим днём. Подробнее об API, ошибках и расчётах — в [backend/README.md](backend/README.md).

## QR с телефона

Подключите телефон и компьютер к одной Wi-Fi сети. Лаунчер определит локальный IPv4 и покажет адрес, например `http://192.168.2.147:5173`. Откройте кабинет, создайте QR сотрудника и сканируйте его камерой телефона.

QR использует сетевой адрес компьютера. Ранее скачанные изображения с `localhost`, прежним IP или старым форматом нужно скачать заново. Для явного выбора сетевого интерфейса задайте `TIPRO_LAN_HOST`. Компьютер и приложение должны оставаться включёнными.

Если адрес не открывается на телефоне, проверьте доступ Node.js в брандмауэре, VPN и изоляцию устройств в гостевой Wi-Fi сети. Локальный адрес недоступен через мобильный интернет; для этого потребуется отдельный хостинг. API и БД слушают loopback, запросы телефона к `/api` проходят через Vue-прокси. Лаунчер передаёт сетевой адрес в `FRONTEND_URL` и доверенные Origin на время запуска, не переписывая `.env`.

## Язык, суммы и даты

Переключатель **Русский / English / 中文** находится на главной, входе, в кабинете и на странице оплаты. Выбор сохраняется в браузере. В настройках ресторана задаётся язык гостевой страницы по умолчанию; собственный выбор гостя имеет приоритет. Авторские названия, имена и тексты целей не переводятся автоматически.

Выбор валюты убран из интерфейса. Новые QR и цели используют валюту ресторана; прежние записи сохраняют свои суммы и валюты. Разные валюты не складываются без конвертации. Символы денег отображаются вместе с локализованным форматированием.

График, история и фильтры используют **часовой пояс браузера**. Vue отправляет `timezone` серверу, который группирует платежи по календарным дням этой зоны. Подписи и суммы графика используют один ключ YYYY-MM-DD. Переключение языка меняет оформление даты, но не её день. В базе время по-прежнему хранится в UTC. Отбор CSV соответствует локальному фильтру, сами временные метки CSV остаются UTC.

## База данных и перенос проекта

В Git находятся [полная SQL-структура](backend/schema/tipro.sql), [инструкция переноса](backend/schema/README.md), миграции и скрипт демонстрационного заполнения. `.env`, реальные аккаунты, платежи, резервные копии и каталог PostgreSQL не публикуются.

На компьютере автора рабочие файлы БД находятся в `backend/.runtime/pgdata`. После восстановления Users.sql 4 ноября 2026 года в базе были исходные 20 ресторанов, 60 сотрудников, 100 платежей и 100 исторических QR. **Клон GitHub не содержит эти рабочие записи**: обычный запуск создаёт пустую базу. Для переноса реальных данных нужен отдельный приватный дамп.

`Users.sql` является бинарным PostgreSQL custom dump и восстанавливается через `pg_restore`, а не `psql -f`. Импортируйте его только в новую пустую базу до миграций. Пошаговые команды для исходного дампа, готового SQL-снимка и Docker находятся в [backend/README.md](backend/README.md) и [backend/schema/README.md](backend/schema/README.md).

Обновить SQL-структуру после изменения миграций:

```sh
npm run db:schema
```

## Необязательные демоданные

Seed запускается отдельно и повторно не перезаписывает существующие записи или пароли. Перед запуском подготовьте окружение и БД через `npm start`.

macOS, из корня:

```sh
cd backend
.venv/bin/python -m app.seed
```

Windows, из корня в PowerShell:

```powershell
Set-Location backend
.\.venv\Scripts\python.exe -m app.seed
```

Seed создаёт доверенные активные деморестораны, сотрудников, цели, QR с демонстрационными чеками и исторические платежи для аналитики. Срок QR не продлевается повторным seed; после его использования или истечения нужен новый код. Пароль новых демоаккаунтов — `DEMO_PASSWORD` из `backend/.env` при первом заполнении.

| Роль | Логин после seed |
| --- | --- |
| Администратор платформы | `admin@tipro.example.com` |
| Менеджеры | `manager1@tipro.example.com`, `manager2@tipro.example.com`, `manager3@tipro.example.com` |
| Сотрудник первого ресторана | `worker11@tipro.example.com` |

Эти аккаунты отсутствуют до явного запуска seed. `DEMO_PASSWORD` не является паролем администратора, созданного командой `create:admin`.

## Проверки

После первоначальной подготовки окружения:

```sh
npm test             # даты графика, переводы, ожидание одобрения, bootstrap и исторический mock
npm run test:backend # интеграционные тесты на отдельной PostgreSQL-базе
npm run build        # production-сборка Vue
```

`pytest` создаёт и удаляет только случайную тестовую базу `tipro_test_*`; рабочие данные не очищает. Тестовому пользователю нужно право CREATEDB. Можно задать `TEST_DATABASE_URL` для отдельного тестового сервера.

Необязательная сквозная проверка через тот же JS-клиент, что использует Vue:

```sh
npm run check:api
```

Для неё нужны работающий API и seed. Проверка создаёт демоцель, проводит оплату 12.50 THB, использует одноразовый QR и проверяет цель, статистику и CSV. При необходимости создаёт новый QR для тестового сотрудника. Она добавляет записи в выбранную демобазу.

```text
backend/app/              # FastAPI, роли, одобрение ресторанов, QR, платежи и аналитика
backend/alembic/          # миграции исходной PostgreSQL-схемы
backend/schema/           # исходная и актуальная структура без приватных записей
backend/scripts/          # окружение, локальная БД, экспорт схемы, demo webhook
backend/tests/            # интеграционные проверки PostgreSQL
src/api/                  # рабочий REST-клиент; mock оставлен для исторических тестов
src/views/                # кабинеты, ожидание одобрения, оплата и настройки
src/components/           # QR, график, таблицы и цели
src/i18n/                 # переводы интерфейса
src/utils/dates.js        # календарные даты графика и часовой пояс браузера
scripts/run-python.mjs    # подготовка локальной .venv и общий вход для npm-команд
scripts/start.py          # запуск БД, миграций, FastAPI и Vue
scripts/check-api.mjs     # сквозная проверка рабочего API-клиента
docker-compose.yml       # необязательный PostgreSQL + FastAPI в контейнерах
```
