# Tipro — онлайн-чаевые

Интерактивный фронтенд платформы для сети «Вкус-Сервис»: Vue 3, Composition API / `<script setup>`, JavaScript, Vite, Vue Router, Pinia, Lucide и клиентская генерация настоящих QR-кодов библиотекой `qrcode`.

## Запуск

Нужен Node.js 20.19+ или 22.12+.

```sh
npm install
npm run dev
```

Откройте адрес, напечатанный Vite (обычно http://localhost:5173).

```sh
npm run build     # production-сборка в dist/
npm run preview   # просмотр production-сборки
npm test          # интеграционные проверки мокового API
```

При размещении на статическом хостинге настройте SPA fallback всех неизвестных URL на `index.html`, чтобы работали прямые ссылки `/app/...` и `/pay/...`. Google Fonts используется необязательно: если сеть недоступна, включается системный шрифт.

## Демонстрация

На главной нажмите «Посмотреть демо», либо в форме входа — «Войти в демо-кабинет». Тестовая учётная запись: `demo@tipro.ru`, пароль `Demo12345`. Кабинет изначально пустой: нет сотрудников, QR-кодов и платежей, показатели равны нулю. Данные появляются только после ваших действий. При первом запуске обновлённой версии прежние демоданные очищаются автоматически; учётные записи и вход сохраняются.

Полный сценарий с чистого листа:

1. Зарегистрируйте ресторан с вымышленным email и тестовым паролем от 8 символов.
2. В разделе «Команда» добавьте сотрудника.
3. В «QR-коды» создайте ему персональный код или QR на конкретный чек.
4. Откройте платёжную ссылку, выберите размер чаевых и нажмите «Оплатить чаевые».
5. Вернитесь в кабинет: история и статистика обновляются при возвращении фокуса. Данные также перечитываются после оплаты в той же вкладке и при входе в кабинет.
6. Для одноразового QR повторите оплату: серверный мок вернёт `USED_QR`. Отказ и отмена одноразовый код не расходуют.

На странице оплаты есть «Пульт демонстрации» с пятью сценариями:

- Успешная оплата — добавляет успешную транзакцию, обновляет сумму и средние чаевые.
- Отказ банка — сохраняет отклонённую транзакцию; сумму можно оплатить снова.
- Недействительный QR — показывает ошибку, не создаёт транзакцию. Реальная проверка: `/pay/missing`.
- Повторная оплата — показывает состояние использованного QR без изменения данных. Реальная проверка: успешно оплаченный QR на чек.
- Отмена — создаёт отменённую транзакцию после запуска обработки. Также можно отменить платёж кнопкой во время обработки. Кнопка «Отменить» до запуска оплаты закрывает форму без создания транзакции.

Демопульт можно скрыть, установив `showDemo = ref(false)` в `PayView.vue`; в production лучше убрать его вместе с тестовыми исходами из платёжного контракта.

Управление сотрудником: редактирование имени/должности, деактивация и статистика. Деактивация блокирует оплату по QR, история сохраняется. В истории доступны фильтры статуса, сотрудника, диапазона дат, пагинация и CSV-экспорт. QR скачивается в PNG, ссылка копируется или выделяется вручную.

В боковом меню «Режим администратора» включает демонстрационный доступ к ресторанам, их сотрудникам, платежам и статистике всей платформы. Повторное переключение возвращает в тестовый ресторан «Вкус-Сервис».

## Ограничения прототипа

Нет настоящих списаний, банка или серверной авторизации. Все данные изолированы в браузере и сохраняются под ключом `tipro-demo-v1`. Мок проверяет границы ресторанов, но не является защитой данных: пользователь может изменить localStorage. Не вводите настоящие пароли. Для тестового входа хранится SHA-256 отпечаток пароля, а не исходный пароль; это не замена серверной аутентификации.

Сгенерированный QR содержит настоящий URL, но созданные данные доступны только в том же браузере на том же origin. Другой телефон не увидит нового сотрудника до подключения общего API. `localhost` в QR обозначает устройство, которое его сканирует: для мобильной демонстрации нужен доступный по сети адрес Vite. Копирование в буфер требует secure context (`localhost` или HTTPS); иначе выделите ссылку вручную. Данные можно сбросить очисткой хранилища сайта в DevTools. При нескольких вкладках мок повторно читает данные перед записью; полноценные транзакции и идемпотентность потребуют сервера.

## Структура

```text
src/
  api/           # единственная точка доступа к данным; mock.js — задержки, валидация, localStorage
  mocks/         # отдельные начальные мерчанты, сотрудники, QR и платежи
  stores/        # Pinia: сессия, данные ресторана, агрегаты, уведомления
  router/        # маршруты, проверки сессии и роли, заголовки страниц
  layouts/       # адаптивный кабинет с боковым меню
  components/    # модальное окно, график, карточки, QR, таблица
  views/         # главная, вход/регистрация, обзор, команда, QR, история, оплата, админ, 404
  utils/         # форматирование сумм, дат и статусов
  style.css      # общая визуальная система и адаптивная вёрстка
 tests/          # проверки связанных сценариев через mockApi
```

## Подключение Python / FastAPI

Компоненты и Pinia импортируют только `api` из `src/api/index.js`. Замените экспорт мокового адаптера реализацией с теми же асинхронными методами и формами ответов. В компонентах нет обращений к localStorage. Рекомендуемые REST-маршруты:

| Метод адаптера | Пример REST |
| --- | --- |
| `session`, `login`, `register`, `logout` | `GET /auth/me`, `POST /auth/login`, `POST /auth/register`, `POST /auth/logout` |
| `workspace` | `GET /workspace` → `{ merchant, employees, qrs, payments }` |
| `saveEmployee` | `POST /employees`, `PATCH /employees/{id}` |
| `createQr`, `toggleQr` | `POST /qrs`, `PATCH /qrs/{id}` |
| `resolveQr` | `GET /public/qrs/{id}` → `{ qr, employee, merchant }` |
| `pay` | `POST /public/qrs/{id}/payments` → транзакция |
| `admin` | `GET /admin/overview` → `{ merchants, employees, payments }` |

Вынесите base URL в `VITE_API_BASE_URL`, используйте `fetch` с `credentials: 'include'` для серверной cookie-сессии, унифицируйте ошибки как `Error` с полями `message` и `code`. Используемые коды: `VALIDATION`, `INVALID_QR`, `USED_QR`, `UNAUTHORIZED`, `STORAGE`. Все суммы сейчас — целые рубли; при переходе на копейки преобразуйте значения на границе адаптера.

Метод `demo` должен остаться только в среде демонстрации. При подключении банка замените симуляцию `pay`: создавайте намерение оплаты на сервере, подтверждайте статус по webhook/polling; отмену реализуйте отдельным серверным запросом. Одноразовость QR проверяйте атомарно на сервере, используйте ключи идемпотентности. Роли, доступ к ресторанам, валидация и безопасность паролей должны обеспечиваться FastAPI. Клиентские route guards предназначены только для интерфейса.
