# Tipro

Фронтенд сервиса онлайн-чаевых для ресторанов. Vue 3, JavaScript, Vite, Vue Router, Pinia. Платежи и серверные запросы имитируются; настоящие деньги не списываются.

## Запуск

Нужен Node.js 20.19+ или 22.12+.

```sh
npm install
npm run dev
```

Откройте адрес Vite (обычно http://localhost:5173).

```sh
npm run build
npm run preview
npm test
```

На статическом хостинге настройте SPA fallback на `index.html`.

## Аккаунты и права

В форме регистрации есть три роли. После входа открывается соответствующий кабинет. Переключателя чужих ролей в кабинете нет.

| Роль | Доступ |
| --- | --- |
| Сотрудник | Только свои чаевые, платежи, средний платёж, график и цели |
| Администратор ресторана (`merchant`) | Вся статистика своего ресторана, команда, приглашения и QR-коды |
| Администратор платформы (`admin`) | Статистика всех ресторанов, сотрудников и платежей |

Гости сканируют QR на чеке ресторана и оставляют чаевые без регистрации. Администратор платформы имеет обзорный кабинет; QR создаёт и отключает только администратор соответствующего ресторана.

В локальном прототипе можно зарегистрировать администратора платформы через общую форму. В production эта роль должна выдаваться только через закрытый серверный процесс. Все роли сейчас проверяются моковым API, но localStorage не обеспечивает настоящую защиту: пользователь может изменить данные в DevTools.

### Сценарий с чистого аккаунта

1. На главной нажмите «Подключить ресторан». Зарегистрируйте администратора: имя, название ресторана, email и тестовый пароль.
2. В «Команда» добавьте сотрудника. Он сразу доступен для выбора гостями; отдельный аккаунт нужен ему для просмотра статистики и управления целями.
3. После добавления сотрудника окно приглашения откроется автоматически. В нём есть отдельный код и готовая ссылка для регистрации. Их также можно получить кнопкой «Приглашение сотрудника» на карточке. Передайте сотруднику код или ссылку; приглашение одноразовое.
4. Сотрудник открывает ссылку, выбирает собственный email и пароль. Аккаунт связывается с существующей записью команды — прежние чаевые сохраняются. Без приглашения сотрудник не может присоединиться к произвольному ресторану. Повторно использовать приглашение нельзя.
5. В кабинете сотрудника откройте «Мои цели». Добавьте цель и сумму. Новая цель становится текущей. Можно хранить несколько целей и выбирать, какую показывать гостям. Изменение цели сохраняет собранные средства; переключение не переносит деньги между целями.
6. Выйдите из аккаунта сотрудника и войдите администратором ресторана. В «QR на чеке» создайте демонстрационный предчек: укажите номер чека и сумму заказа. Нажмите «Посмотреть чек», чтобы увидеть QR внизу чека, скачать весь макет в PNG или распечатать его. QR ведёт на `/restaurant/{merchantId}?qr={qrId}`.
7. Откройте ссылку QR, выберите сотрудника и оставьте демочаевые. Регистрация гостя не нужна.
8. Сотрудник увидит платёж только в своей статистике, администратор ресторана — в общей статистике команды. Администратор платформы — в обзоре всей платформы.

При демонстрации в нескольких вкладках учитывайте, что сессия общая для одного браузера/origin: вход другим пользователем меняет аккаунт во всех вкладках. При возвращении фокуса и переходах кабинеты перечитывают сессию и данные; запрещённый маршрут перенаправляет в кабинет текущей роли. Для одновременной демонстрации разных аккаунтов используйте отдельные профили браузера, но после подключения общего API: локальные данные в разных профилях не общие.

### Цели и оплата

Сотрудник может добавлять и редактировать только свои цели. В публичный ответ попадает только текущая цель, без приглашений, учётных данных и списка личных целей. Успешные чаевые после создания цели увеличивают её прогресс. Отказы и отмены сохраняются в истории, но не увеличивают сумму полученных чаевых и цель. Чаевые, полученные до создания цели, в её прогресс не включаются.

В «Настройки демооплаты» на гостевой странице доступны успех, отказ, неверный QR и отмена. Отмена во время обработки создаёт отменённый платёж; отмена до обработки — нет. QR многоразовый: повторная намеренная оплата допустима. Неактивный сотрудник скрывается от гостей; его вход и действия блокируются, история сохраняется.

### Существующие данные

Используется ключ `tipro-demo-v1`, схема версии 4. С версии 3 сохраняются рестораны, сотрудники, история, QR и цели. Существующие аккаунты ресторанов продолжают входить с прежними паролями. Старые ссылки `/employee/{token}` перенаправляются на регистрацию по приглашению; редактирования целей без входа больше нет.

Для ранее созданного пустого тестового ресторана сохранён вход `demo@tipro.ru` / `Demo12345`. Технический тестовый аккаунт платформы: `admin@tipro.demo` / `Demo12345`. Исторический метод API `demo` оставлен для разработки и не представлен переключателем ролей в интерфейсе. При старой схеме версии 1 выполняется прежняя одноразовая очистка стартовых демоданных; дальнейшие миграции рабочие данные сохраняют.

## Ограничения

Все данные и сессия хранятся в браузере на конкретном origin. Другой телефон или профиль браузера не увидит созданный ресторан и QR без общего бэкенда. Для демонстрации используйте «Открыть» на карточке QR в том же браузере. Макет предчека не является фискальным кассовым чеком: реальное добавление QR в чек потребует интеграции с кассовой системой. Заказ и чаевые оплачиваются отдельно. QR остаётся многоразовым. `localhost` на телефоне обозначает сам телефон. Копирование в буфер требует localhost/HTTPS, иначе выделите ссылку вручную.

Используйте вымышленные данные и тестовые пароли. В браузере сохраняется SHA-256 отпечаток пароля; это не полноценная серверная авторизация и не замена безопасному хранению паролей на сервере.

## Подключение FastAPI

Замените экспорт адаптера в `src/api/index.js` реализацией с теми же асинхронными методами. Компоненты не работают с localStorage напрямую. Base URL можно вынести в `VITE_API_BASE_URL`; для серверных cookie используйте `credentials: 'include'`.

| Метод | Пример REST |
| --- | --- |
| `session`, `login`, `register`, `logout` | `GET /auth/me`, `POST /auth/login`, `/auth/register`, `/auth/logout` |
| `invitation` | `GET /invitations/{token}` → только название ресторана, имя и должность |
| `workspace` | `GET /workspace` → `{ user, merchant, employees, qrs, payments }` с фильтрацией на сервере |
| `saveEmployee` | `POST /employees`, `PATCH /employees/{id}` — администратор своего ресторана |
| `saveGoal`, `activateGoal` | `POST /employees/me/goals`, `PATCH /employees/me/goals/{id}`, `PUT /employees/me/active-goal` — только сам сотрудник |
| `createQr`, `toggleQr` | `POST /qrs` с `{ receiptNumber, billAmount }`, `PATCH /qrs/{id}` — администратор своего ресторана |
| `resolveRestaurant` | `GET /public/restaurants/{merchantId}?qr={qrId}` |
| `pay` | `POST /public/qrs/{qrId}/payments` → `{ employeeId, amount }` |
| `admin` | `GET /admin/overview` — только администратор платформы |

Самостоятельную регистрацию роли `admin` и методы `demo` убрать из production. Роль, принадлежность ресторану и идентичность сотрудника сервер определяет из сессии, а не доверяет входным параметрам. Приглашения должны иметь срок действия, отзыв и атомарное однократное использование. Пароли обрабатываются только безопасными серверными алгоритмами.

Суммы прототипа — целые рубли. Ошибки адаптера имеют `message` и `code`: `VALIDATION`, `UNAUTHORIZED`, `INVALID_QR`, `INVALID_EMPLOYEE`, `INVALID_ACCESS`, `STORAGE`. Для реального банка нужны серверное создание платежа, webhook, идемпотентность и транзакционное обновление прогресса цели. Клиентские guards ограничивают интерфейс; защита данных обязательна на сервере.
